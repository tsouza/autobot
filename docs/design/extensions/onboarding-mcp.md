# Extension — onboarding MCP server

Intent: let a person onboard a project from its working directory with any MCP-capable coding agent. The agent analyses the directory, interviews the person until every required attribute is settled, and submits the result to an AutoBot installation as proposals, which a human then accepts through the CLI (THESIS goal 6, I-8).
Gate: the server, its tools, resources and interview prompt at **M0-Q**; charter candidates extracted from repository content at **G-INTAKE**; repository creation at **G-FORGE**.

Relies on (kernel): the intake client, the intake-submitter identity, sourced values and human acceptance (ONBOARD §1, TRUST, F-43, F-44); the command and receipt protocol with a client-persisted idempotency key and create identity (KERNEL §2, F-1, F-2, F-5); forge verification of a proposed repository (ONBOARD §2).

Decisions:

- **One local server, one identity.** `autobot-mcp` is a Model Context Protocol server that the coding agent starts as a local process over the stdio transport, rooted at the directory it is started in. It fills the intake-client role of ONBOARD §1. It reads that directory and its git metadata and never writes them, and it reaches one installation's Kubernetes API only with the credential of the intake-submitter identity of the namespace it submits to. It decides nothing: every tool result is a read of the local directory or of AutoBot status.
- **Tools.** Every tool declares a JSON Schema `inputSchema` and `outputSchema`. `inspect_directory` carries the `readOnlyHint` annotation; every submit tool carries `destructiveHint` false, because it only creates or revises proposals.

  | Tool | Effect |
  |---|---|
  | `inspect_directory` | Lists the directory's files with the content digests the server computes, and its git state: remotes, branch, head commit, whether head is pushed, and every uncommitted, untracked or unpushed path. |
  | `submit_intake` | Creates or revises the `Intake`; for a new context, in the intake namespace and carrying the proposed `WorkContext.spec` configuration. |
  | `submit_adoption` | Creates or revises the proposed `Project` and `Repository` resources, or names an existing project to attach. |
  | `submit_brief` | Creates a `WorkBrief` for one document the person confirmed: its content, which the Intake controller stores as the brief's artifact, or a path at a pushed commit of a proposed repository, with its content digest either way. |
  | `submit_charter` | Creates or revises a `PROPOSED` revision of the context's `Charter` or of a project's `ProjectCharter`, both of which the Intake controller creates. |
  | `submit_plan` | Creates or revises the `PlanProposal`; for a later brief it names the plan and the revision it revises. |

  Every submit returns, as structured content, its command receipt and the resulting status and conditions of what it wrote.
- **Schemas are generated, never written.** The `inputSchema` of each submit tool is the schema of its kind's spec, generated from the same Rust types (`autobot-api`) that generate the CRD's structural schema, which admission validates against; every attribute field is a sourced value. The server validates a submission before sending it, and admission validates it again, so a server whose schemas drifted is refused, never trusted. A proposal is complete exactly when it validates.
- **Resources.** `autobot://schema/{kind}` is the generated schema of each intake kind, with a description of every field; it is where the interview's questions come from. `autobot://intake/{name}` is the status and conditions of an `Intake` and of every proposal it holds — a repository the forge did not verify, a brief digest that did not match, a plan proposal whose base revision is no longer active, and for a later brief the project's plan and active revision — and supports subscription, so the agent learns when an accept or a verification lands. Both are resource templates; the intake-submitter identity can read nothing else.
- **The interview is the `onboard` prompt.** Its one optional argument, `project`, names an onboarded project for a later brief. Its messages direct the agent to call `inspect_directory` and read the schema resources; to settle each required attribute from the directory where the directory settles it, recording the path, digest and trust label; to ask the person, one question at a time, for every attribute that remains, until none is left; to ask which documents form the brief and to confirm each; to raise every uncommitted or unpushed path as a question — commit and push it, or leave it out — and, for a repository that does not exist yet, to have the person create it outside AutoBot; to submit in the order intake, adoption, briefs, charters, plan, waiting for the context configuration's acceptance first when it proposes a new context; and to end by giving the person the CLI commands that accept the proposals. For the context's `Charter` the prompt asks for every entry and records only the person's answers. The prompt is guidance to an untrusted agent; nothing depends on the agent following it, because admission and the Intake controller enforce every rule it states.
- **Provenance is attached where it is known.** Directory content is `UNTRUSTED_REPOSITORY_CONTENT` with its path, its commit when committed, and a digest the server computes itself, never one the agent relays; issue and pull-request text the agent read with its own forge access is `UNTRUSTED_ISSUE_OR_PR_TEXT` with its URL and the digest the agent reports; the person's answer is `INTERVIEW_ANSWER` with the digest of the question and the answer. A digest the server did not compute is the agent's claim, and an answer or a confirmation the agent relays is no act of the person: the person's act is the accept through the CLI.
- **Every submission is a command.** Each submit is an `AutoBotCommand` whose client request key the server persists outside the working directory; a retry after an unknown result looks the key up, never resubmits under a new one (KERNEL §2). The `client` field carries the server's name and version and the name the agent reports; the principal is always the authenticated intake-submitter identity.
- **What it never does.** No tool accepts, rejects, activates or grants anything, and none deletes a resource. No tool creates a forge repository; until G-FORGE the person creates it outside AutoBot and onboarding adopts it. No tool uploads anything from the working directory except the brief documents the person confirmed, and the server never takes custody of the directory or writes it.
